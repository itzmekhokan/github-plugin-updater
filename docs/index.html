The problem

Ship from GitHub, update like wp.org

Composer VCS repositories can install a GitHub plugin — but updating still means a developer running composer update over SSH. Site owners get no update badge, no changelog, no one-click button.

This library flips that around. It checks your GitHub releases (or tags) at runtime and surfaces available updates directly in the WordPress admin — the exact same experience your users already know from the plugin screen.

Everything happens inside the plugin you already ship. There is no companion plugin to install and nothing to configure at the site level beyond a token for private repos.

# Plugins → Updates, in wp-admin
Awesome Plugin
  Installed: 1.4.0  →  Available: 1.5.0
  [ View details ]   [ Update now ]

# ...served straight from your GitHub release.

What you get

Features

A focused, dependency-light library that behaves exactly like a native WordPress update source.

🔄

Native update UX

Update badge, "View details" modal, and one-click "Update now" — identical to a wp.org-hosted plugin.

🔐

Private & org repos

Public repos work anonymously. Private and organization repos authenticate with a Personal Access Token.

🏷️

Releases or tags

Track GitHub releases (default) or fall back to tags. Optionally prefer an uploaded .zip asset over the source zipball.

⚡

Zero-config boot

Add an Update URI header, call one line, and you're done. Or declare config once in composer.json.

🧭

Rate-limit friendly

Responses are cached for 12 hours and revalidated with ETags, staying well under GitHub's anonymous limit.

📦

Folder-safe installs

Renames GitHub's owner-repo-<hash>/ archive folder to your real plugin slug so updates land cleanly.

Get started

Install & boot in three steps

Require the library, point it at your repository, boot from your main plugin file.

Require it

Add the Composer package to your plugin.

Point at your repo

Via a header, PHP config, or composer.json.

Boot & ship

One line from your main file. Updates appear automatically.

terminal 
composer require itzmekhokan/github-plugin-updater

Zero-config (header-driven)

Add an Update URI header pointing at your repo, then boot from the main file:

awesome-plugin.php 
/**
 * Plugin Name: Awesome Plugin
 * Version:     1.4.0
 * Update URI:  https://github.com/acme/awesome-plugin
 */

require __DIR__ . '/vendor/autoload.php';

\Itzmekhokan\GitHubPluginUpdater\Bootstrap::auto( __FILE__ );

Configuration

Explicit config, your way

Prefer to be explicit? Pass options in PHP, or declare them once in composer.json and keep calling Bootstrap::auto().

PHP 
\Itzmekhokan\GitHubPluginUpdater\Bootstrap::boot( __FILE__, [
  'repository'        => 'acme/awesome-plugin',
  'source'            => 'release', // or 'tag'
  'prefer-asset'      => true,      // use uploaded .zip
  'allow-prereleases' => false,
  'token'             => 'env:GH_UPDATER_TOKEN',
] );
composer.json 
{
  "extra": {
    "github-plugin-updater": {
      "repository":        "acme/awesome-plugin",
      "source":            "release",
      "prefer-asset":      true,
      "allow-prereleases": false,
      "token":             "env:GH_UPDATER_TOKEN"
    }
  }
}
OptionDefaultWhat it does
repository—owner/repo on GitHub (inferred from the Update URI header when omitted).
sourcereleaseTrack GitHub releases, or set tag to track pushed tags.
prefer-assetfalsePrefer an uploaded release .zip asset over the auto-generated source zipball.
allow-prereleasesfalseOffer draft/pre-release versions as updates.
token—Token spec for private repos (see below). Omit for public repos.

Authentication

Private & organization repositories

Provide a GitHub Personal Access Token with repo scope (or fine-grained Contents: read). The token value is a spec — where to read the token from, never the token itself in code.

SpecReads from
env:VAREnvironment variable VAR
constant:NAMEPHP constant NAME (define it in wp-config.php)
optionA WordPress option (plain storage in v1.0 — see note)

If no per-plugin token is set, a global constant is used as a fallback — so a site owner can configure one token for every managed plugin at once:

wp-config.php 
// Fallback token for all managed plugins
define( 'GITHUB_PLUGIN_UPDATER_TOKEN', 'ghp_xxx' );
Note: the option source stores the token as a plain option in v1.0. Prefer env / constant in production. Encrypted at-rest storage lands in v1.1.

Under the hood

How it works

Four WordPress hooks do all the work — no cron, no external service, no phone-home.

📥

pre_set_site_transient_update_plugins

Injects the "update available" record so WordPress shows the badge and the version bump.

📄

plugins_api

Serves the "View details" modal, rendering your GitHub release notes as the changelog.

📁

upgrader_source_selection

Renames GitHub's owner-repo-<hash>/ folder to your plugin slug so the update installs in place.

🔑

upgrader_pre_download

Downloads private archives with the correct two-step auth dance — auth to the API host, dropped on the signed redirect.

Every response is cached for 12 hours and revalidated with ETags, so the checker stays comfortably under GitHub's 60 req/hr anonymous rate limit.
